## 1. Encoder precision (fp32 / fp16 / int8)

400 images from the chaos dataset, pre-decoded (≤1024 px), batch 32, `intra_op_num_threads=4`. *Model* = ONNX vision tower only on pre-processed pixels; *end-to-end* = `encode_images()` incl. resize/crop/normalise. Agreement is measured against fp32 on the same images; top-10 overlap = mean |top10(prec) ∩ top10(fp32)| / 10 over 20 text queries.

| precision | model img/s | end-to-end img/s | preprocess ms/img | text query p50 / p99 ms | image cos vs fp32 (mean / min) | text cos vs fp32 | top-10 overlap | load s |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **fp32** | 46.9 | 34.5 | 3.48 | 11.0 / 48.9 | 1.0 / 1.0 | 1.0 | 1.0 | 1.15 |
| **fp16** | 10.5 | 13.2 | 4.32 | 15.2 / 37.6 | 1.0 / 1.0 | 1.0 | 1.0 | 1.22 |
| **int8** | 52.7 | 40.6 | 3.61 | 2.8 / 15.4 | 0.9452 / 0.8509 | 0.9286 | 0.575 | 0.4 |

Fastest image encoder on this CPU: **int8** (1.12× fp32). fp16 has no fast kernels on x86 CPUs (ONNX Runtime inserts casts), so it is mainly useful for GPU / disk size; int8 (dynamic quantisation) is the fastest and loads 3× faster with the fastest text queries, but it is a lossy approximation: image-embedding cosine to fp32 is only ~0.95 and text-query top-10 overlap with fp32 is ~0.58, so fp32 is the better choice when retrieval fidelity matters more than ~10-20 % throughput.

## 4. Duplicate detection

`GET /duplicates` logic (`app.dedup.find_duplicates`) on the full 3000-image chaos index (`data/demo_index`, int8 CLIP), scored against the 300 planted pairs in `ground_truth.json` (5 % exact copies, 5 % near copies: resize / re-encode / crop / brightness, alone or combined). A pair is recalled when both files land in the same group; pair precision counts within-group pairs that belong to one planted family. *cold* = first call (pixel verification of all candidates), *warm* = repeat call (pair-score cache).

| setting | recall | exact | near | pair precision | groups | images in groups | largest groups | cold ms | warm ms |
|---|---:|---:|---:|---:|---:|---:|---|---:|---:|
| default (verified) | **0.953** | 1.000 | 0.907 | 0.356 | 307 | 707 | [20, 16, 10, 10, 9] | 13521 | 488 |
| pHash only | **0.807** | 1.000 | 0.613 | 0.659 | 257 | 549 | [10, 10, 4, 3, 3] | 2160 | 112 |
| cosine only | **0.953** | 1.000 | 0.907 | 0.417 | 299 | 669 | [20, 16, 9, 5, 5] | 13992 | 437 |
| raw rule, no verification | **0.907** | 1.000 | 0.813 | 0.002 | 228 | 2182 | [282, 270, 218, 210, 94] | 262 | 306 |

Near-duplicate recall by transform (default setting): brightness 18/19, brightness+crop 9/12, brightness+reencode 12/12, brightness+resize 10/11, crop 17/21, crop+reencode 10/13, crop+resize 10/12, reencode 20/20, reencode+resize 9/9, resize 21/21

On this synthetic library the raw PRD rule (pHash ≤ 6 OR cosine ≥ 0.95) chains thousands of same-template images (slides of one deck, screenshots of one app, generated forests) into a few giant groups: int8 CLIP puts them at cosine 0.95-0.98 while a 5 % crop of the same image can drop to ~0.90. The default therefore widens the cosine search to ≥ 0.88 and verifies every near candidate on the thumbnails (mean-chromaticity check + brightness-invariant colour correlation after a crop-alignment search, see `app/dedup/verify.py`).

## Tuning knobs

| env var | default | effect |
|---|---|---|
| `VS_ONNX_PRECISION` | `fp32` | `fp32` / `fp16` / `int8` model files |
| `VS_BATCH_SIZE` | `32` | images per embed batch = pipeline chunk size |
| `VS_ONNX_THREADS` | cpu_count | ONNX intra-op threads |
| `VS_ONNX_INTER_THREADS`, `VS_ONNX_EXEC_MODE` | unset, `sequential` | ONNX inter-op parallelism |
| `VS_ONNX_SPIN` | ORT default | `0` disables intra-op thread spinning (frees cores for OCR) |
| `VS_INDEX_WORKERS` | cpu_count | decode/colour/OCR/hash thread-pool size |
| `VS_OCR_ENGINE` | `auto` | `none` skips OCR (largest single cost) |
